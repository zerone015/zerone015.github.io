이번 글에서는 물리 메모리를 초기화하는 과정과, 물리 페이지를 관리하는 버디 할당자를 정리한다.

## Initialization

물리 메모리 초기화 코드: [src/kernel/pmm.c](https://github.com/zerone015/kfs/blob/master/src/kernel/pmm.c#L518)

```c
#define MAX_MMAP    62

struct mmap_buffer {
    multiboot_memory_map_t regions[MAX_MMAP + 2];
    size_t count;
};

uintptr_t pmm_init(multiboot_info_t *mbd)
{
    struct mmap_buffer mmap;

    mmap_copy_from_grub(&mmap, mbd);
    mmap_trim_highmem(&mmap);
    mmap_reserve_kernel(&mmap);
    mmap_align(&mmap);
    return __pmm_init(&mmap);
}
```

GRUB이 넘겨준 메모리 맵을 복사한 뒤 쓸 수 있는 형태로 다듬고, 마지막에 버디 할당자를 초기화한다.

### mmap_copy_from_grub

부팅 과정에서 `multiboot_info` 구조체의 주소는 가상 주소로 바꿔서 `kmain`에 넘겼지만, 그 안에 들어 있는 메모리 맵(`multiboot_memory_map_t`)의 주소는 여전히 물리 주소다. 그래서 메모리 맵을 읽기 위해 이 주소를 가상 주소 공간에 잠깐 매핑한다.

그다음 메모리 맵을 `struct mmap_buffer`에 복사한다. GRUB은 BIOS에게서 메모리 정보를 받아 올 때 사용 가능한 영역에 이 정보를 저장했고, 그 영역은 메모리 맵에서도 여전히 사용 가능한 영역으로 표시되어 있다. 이대로 쓰면 초기화 도중에 그 영역이 다른 용도로 할당되어 메모리 맵이 덮어써질 수 있다. 이 정보는 물리 메모리를 초기화하는 동안에만 쓰이기 때문에, 그 영역을 따로 예약하기보다는 `pmm_init`의 스택 프레임에 복사해서 쓰고 버리는 쪽을 택했다.

### mmap_trim_highmem

물리 메모리 관리를 처음 설계할 때 PAE를 고려하지 않았기 때문에, 4GB 위의 물리 메모리에는 접근할 수 없다. 그래서 4GB 위에서 시작하는 영역은 예약된 영역으로 바꾸고, 4GB 경계에 걸친 영역은 4GB까지로 잘라 낸다.

### mmap_reserve_kernel

커널 이미지가 적재된 영역도 메모리 맵에서는 사용 가능한 영역으로 표시되어 있다. 이 영역은 커널 이미지가 계속 차지하므로 사용 가능한 영역에서 제외한다.

커널은 물리 주소 1MB에 적재되고, 1MB 바로 아래는 BIOS 영역이라 항상 예약되어 있다. 따라서 커널이 들어 있는 사용 가능 영역은 항상 1MB에서 시작하므로, 그 영역의 앞부분을 커널 크기만큼 잘라 낸다.

### mmap_align

BIOS가 제공한 메모리 맵의 영역들은 시작과 끝이 페이지 크기로 정렬되어 있지 않다. 사용 가능한 영역을 버디 할당자에 페이지 단위로 넣으려면 페이지 크기로 정렬되어 있어야 한다. 그래서 각 영역의 시작 주소를 페이지 크기로 올림한다. 끝은 나중에 버디 할당자에 페이지를 넣을 때 내림한다.

### __pmm_init

먼저 PFN을 인덱스로 하는 `struct page` 배열인 `pgmap`을 할당한다.

```c
struct page {
    uint32_t order;
    uint32_t ref;
    uint32_t flags;
    struct list_head free_list;
};

struct page *pgmap;
```

`pgmap`은 버디 할당자가 각 페이지의 상태를 관리하는 데 쓰고, COW로 공유되는 페이지의 참조 카운트를 세는 데도 쓴다.

사용 가능한 모든 페이지를 PFN으로 바로 찾을 수 있도록, 배열 크기는 사용 가능한 영역 중 가장 높은 주소에 있는 영역의 끝을 기준으로 잡는다. 이 시점에는 아직 물리 메모리 관리자가 없기 때문에, 메모리 맵에서 이 크기를 담을 수 있는 영역 중 가장 큰 영역을 찾아 `pgmap` 전용으로 예약하고 가상 주소 공간에 매핑한다. 가장 큰 영역을 고르는 건 단편화를 최대한 줄이기 위해서다.

커널 공간은 4MB 페이지를 쓰기 때문에 `pgmap`도 4MB 단위로 예약하고 매핑한다. 그래서 `pgmap`을 매핑한 마지막 4MB 페이지에는 빈 공간이 남을 수 있는데, 이 남는 공간이 커널 힙의 시작 지점이 된다.

![물리 메모리 초기화 직후의 커널 가상 주소 공간](/assets/img/kfs/kfs-pmm.png)
_Kernel virtual address space after physical memory initialization_

그다음 테스트 코드에서 쓰는 메모리 정보 구조체에 사용 가능한 페이지 수를 기록한다.

```c
struct meminfo {
    size_t usable_pages;
};
```

마지막으로 페이지 크기로 정렬된 사용 가능 영역들을 버디 할당자에 넣는다. 이때 부팅 속도를 위해 영역 크기를 보고 가능한 한 큰 order의 블록 단위로 넣는다.

## Buddy Allocator

KFS 과제 PDF에서도 참고하라고 하고 유용한 정보가 많기 때문에, 만들던 당시 OSDev를 많이 참고했다. OSDev는 운영체제 개발의 진입 장벽을 낮추기 위해, 매뉴얼을 일일이 뒤지지 않으면 알기 힘든 정보들을 정리해 둔 OS 개발 커뮤니티다. 메모리 할당자를 구현할 때도 OSDev Wiki와 Forum을 참고했는데, 위키의 [Page Frame Allocation](https://osdev.wiki/wiki/Page_Frame_Allocation) 글에서는 물리 메모리 할당자 후보로 크게 비트맵, free stack, 버디 할당 시스템 세 가지를 소개한다.

내용을 정리하면 비트맵은 메모리를 가장 아낄 수 있지만 느리고, free stack은 가장 빠르지만 페이지 상태를 추적할 수 없어서 다중 페이지 크기를 지원할 수 없다. 버디 할당 시스템은 리눅스가 사용하는 할당자로, 비트맵과 비슷하지만 페이지 블록 단위로 더 빠르게 찾을 수 있다. 나는 리눅스의 할당자라는 점에도 관심이 있었고 다중 페이지 크기 지원도 염두에 두고 있었기 때문에 버디 할당 시스템을 선택했다.

버디 할당 시스템은 블록 크기별로 메모리를 관리하고, 이 단위를 order라고 부른다. order 0은 가장 작은 크기인 4KB 페이지를 다루고, order가 1 증가할 때마다 블록 크기는 2배가 된다. 즉 order $k$의 블록 크기는 $4\text{KB} \times 2^k$로, 항상 페이지 크기의 2의 거듭제곱 배다.

하나의 블록은 같은 크기의 두 블록으로 쪼개지고, 이 두 블록이 서로의 버디가 된다. 두 버디가 모두 비면 다시 하나로 합쳐진다. 이런 원리로 버디 할당 시스템은 블록을 분할하고 병합하면서 요청된 크기의 메모리를 제공하고, 해제할 때 버디와 병합하면서 외부 단편화를 줄인다. 다만 외부 단편화를 완전히 없애지는 못한다. 예를 들어 0~3번 페이지 중 1번과 2번만 비어 있으면, 두 페이지는 붙어 있지만 서로 버디가 아니라서 합쳐지지 않는다. 그래서 8KB 요청이 와도 이 공간을 줄 수 없다.

또 요청 크기가 2의 거듭제곱이 아니면 올림해서 할당하기 때문에 내부 단편화가 생길 수 있다. 하지만 커널의 물리 페이지 할당자로 쓸 때는 내부 단편화 문제가 거의 발생하지 않는다. 바이트 단위의 작은 할당은 그 위의 힙이 처리하고, 버디 할당자에는 페이지 단위로 요청이 들어오기 때문이다. 드라이버가 DMA를 위해 12KB처럼 2의 거듭제곱이 아닌 크기의 연속된 메모리를 요청하는 경우에도, 16KB 블록을 4KB 페이지 4개로 쪼갠 뒤 3개만 주고 나머지 1개는 반납하면 된다.

위키에서는 비트맵 기반 버디 할당 시스템을 설명하고 있다. 내 버디 할당 시스템에는 두 가지 버전이 있는데, 처음 구현한 버전이 이 비트맵 기반 버디 할당 시스템이다.

### Bitmap-based Buddy Allocator

order마다 비트맵이 하나씩 있고, 각 비트의 오프셋은 해당 order 크기 블록의 번호를 의미한다. order가 1 증가할 때마다 블록 크기가 2배가 되므로 비트맵의 크기는 절반으로 줄어든다. 즉 각 order의 비트맵 크기는 공비가 1/2인 등비수열이다. order 0 비트맵의 크기가 $a$, order의 개수가 $n$이라면 전체 크기는 다음과 같다.

$$
a\frac{1-(1/2)^n}{1-1/2} = 2a\left(1-\frac{1}{2^n}\right)
$$

즉 단순한 비트맵보다 메모리를 약 2배 사용한다.

![order별 비트맵 구조](/assets/img/kfs/kfs-buddy-bitmap.png)
_Per-order bitmaps after splitting_

비트맵 기반 버전의 할당과 해제 코드: [src/pmm.c](https://github.com/zerone015/kfs/blob/df24f0115030f61fb19758ce47ebe31dc1d9f112/src/pmm.c#L244)

```c
struct buddy_order {
    uint32_t *bitmap;
    size_t free_count;
};

struct buddy_allocator {
    struct buddy_order orders[MAX_ORDER];
};
```

각 order의 비트맵에서 비트가 1이면 그 블록이 사용 가능하다는 뜻이고, `free_count`는 해당 order에서 사용 가능한 블록의 개수다.

할당은 요청 크기로 order를 찾고 해당 order의 `free_count`를 확인한다. 사용 가능한 블록이 있으면 그 order의 비트맵을 순회해 블록을 할당하고, 없으면 상위 order에서 찾는다. 상위 order에서 찾은 경우에는 블록을 분할하는데, 하위 order에서의 오프셋은 원래 오프셋에 2를 곱한 값이다. 분할은 항상 쌍의 왼쪽 블록을 계속 나누며, 하위 order로 내려갈 때마다 버디의 오프셋을 XOR 1 연산으로 구해 그 비트를 설정해서 사용 가능으로 표시한다. 최종적으로 할당되는 블록은 쌍의 왼쪽 블록이다.

![비트맵 버전에서 할당할 때 블록을 분할하는 과정](/assets/img/kfs/kfs-buddy-bitmap-split.png)
_Splitting order 2 block #1 to allocate page 4_

해제 역시 먼저 해제할 메모리의 크기로 order를 찾는다. 해당 order에서 버디가 사용 가능한 상태이면 병합을 위해 버디의 비트를 클리어하고 상위 order로 올라간다. 상위 order에서의 오프셋은 2로 나누어 구한다. 이렇게 계속 올라가다가 버디가 사용 불가능하면 더 이상 병합할 수 없으므로, 그 order에서 해제한 블록의 비트를 설정하고 멈춘다.

![비트맵 버전에서 해제할 때 버디와 병합하는 과정](/assets/img/kfs/kfs-buddy-bitmap-merge.png)
_Freeing page 5 and merging up to order 2 block #1_

할당할 때는 비트맵을 32비트 워드 단위로 읽어서 값이 0이 아닌지만 확인하는 방식으로 탐색을 줄였지만, 여전히 비트맵을 앞에서부터 훑어야 해서 시간 복잡도는 $O(N)$이었다. 해제는 병합하면서 order를 하나씩 올라가므로 $O(\log N)$이고, 병합할 버디가 없으면 $O(1)$이다.

물리 페이지 할당자는 페이지 폴트가 날 때마다 호출될 만큼 자주 불리는 함수라 작은 오버헤드도 크게 쌓인다. 그래서 할당에 $O(N)$이 걸리는 건 받아들이기 어려웠고, 이를 개선한 다음 버전으로 넘어갔다.

### Free list-based Buddy Allocator

할당과 해제 코드: [src/kernel/pmm.c](https://github.com/zerone015/kfs/blob/master/src/kernel/pmm.c#L434)

```c
struct page {
    uint32_t order;
    uint32_t ref;
    uint32_t flags;
    struct list_head free_list;
};

struct page *pgmap;

struct buddy_order {
    struct list_head free_list;
};

struct buddy_allocator {
    struct buddy_order orders[MAX_ORDER];
};
```

`struct buddy_order`에서 `bitmap`과 `free_count`를 없애고 `free_list`를 추가했다. 또 각 페이지를 나타내는 `struct page`와, 시스템의 메모리 크기만큼 `struct page`를 담은 배열 `pgmap`을 추가했다.

`free_list`는 사용 가능한 블록들을 잇는 연결 리스트이고, `struct page`끼리 연결된다. 그래서 탐색 없이 리스트의 헤드에서 바로 블록을 꺼내 할당할 수 있다. 페이지를 구조체로 만든 건 각 페이지에 연결 리스트의 링크를 넣어야 했기 때문이다. `pgmap`은 버디의 `struct page`를 바로 찾는 데 쓰인다. 원래는 PFN을 인덱스로 하는 정수 배열로 페이지의 참조 카운트를 따로 관리했는데, 이것도 `struct page` 안에 참조 카운트를 넣는 것으로 대체했다.

order 1 이상의 블록은 그 블록에 속한 `struct page`들 중 가장 왼쪽 페이지가 블록 전체를 대표한다. `flags`에는 현재 `PAGE_FREE`만 있고, 이 플래그는 그 블록이 사용 가능한 상태라는 뜻이다.

![pgmap과 order별 free_list의 구조](/assets/img/kfs/kfs-buddy-freelist.png)
_pgmap and per-order free\_list_

할당은 요청 크기에 맞는 order를 구한 뒤, 그 order부터 상위 order로 올라가며 `free_list`가 비어 있지 않은 order를 찾는다. 상위 order에서 찾았다면 마찬가지로 분할한다. 분할은 항상 쌍의 왼쪽 블록을 나누기 때문에, 분할할 때마다 해당 order에서 오른쪽 블록이 사용 가능한 상태가 된다. 이 구조에서 왼쪽을 나누면 대표 페이지가 바뀌지 않는다는 장점이 있다. 오른쪽 블록, 즉 왼쪽의 버디는 왼쪽 블록의 PFN에 현재 order의 블록 페이지 개수를 더해서 구한다. 하위 order로 내려가도 달라지는 건 없다. 대표 페이지의 PFN은 그대로이고 블록의 페이지 개수만 절반으로 줄어들기 때문에, 같은 계산으로 하위 order의 버디가 자연스럽게 나온다.

![할당할 때 블록을 분할하는 과정](/assets/img/kfs/kfs-buddy-split.png)
_Splitting an order 2 block (PFN 8–11) to allocate PFN 8_

해제도 먼저 order를 구한 뒤, 병합할 수 있는지 확인하기 위해 버디를 찾는다. 해제할 때는 해제하는 블록이 쌍의 왼쪽인지 오른쪽인지 알 수 없다. 그래서 다른 방법으로 버디를 구하는데, 해제하는 블록의 PFN에 블록 페이지 개수를 XOR하면 버디의 PFN이 나온다. 쌍의 오른쪽이면 페이지 개수만큼 빼고, 왼쪽이면 더하면 버디의 PFN이 되는데, 이것이 XOR 연산과 같다.

```c
buddy_pfn = pfn ^ bpages;
```

이렇게 찾은 버디가 사용 가능한 상태이면, 병합을 위해 버디를 `free_list`에서 빼고 사용 불가 상태로 바꾼 뒤 상위 order로 올라간다.

병합된 블록의 대표 페이지는 항상 쌍의 왼쪽 블록의 대표 페이지다. 한 order에서 블록의 PFN은 항상 그 order의 블록 페이지 개수의 배수이므로, 이 대표 페이지의 PFN은 현재 PFN을 페이지 개수의 2배로 내림 정렬해서 구한다.

```c
pfn = align_down(pfn, 2 * bpages);
```

물론 병합된 블록이 상위 order에서 쌍의 왼쪽일지 오른쪽일지는 알 수 없기 때문에, 버디는 다시 XOR로 구한다. 병합이 끝나면 그 블록은 사용 가능한 상태가 되어 해당 order의 `free_list`에 추가된다.

![해제할 때 버디와 병합하는 과정](/assets/img/kfs/kfs-buddy-merge.png)
_Freeing PFN 5 and merging up to an order 2 block (PFN 4–7)_

할당은 `free_list`의 헤드에서 바로 꺼내므로 $O(1)$이고, 분할이 필요할 때만 order 수만큼 내려가 $O(\log N)$이다. 해제도 `pgmap`으로 버디의 `struct page`를 바로 찾을 수 있어서, 병합이 필요 없으면 $O(1)$이고 병합이 필요할 때만 $O(\log N)$이다.

마지막으로 두 버전의 메모리 사용량을 비교해 보면, 물리 페이지 수를 $N$이라고 할 때 $N = \text{RAM} / 4\text{KB}$다.

비트맵 버전에서 order 0 비트맵은 페이지 하나당 1비트이므로 $a = N/8$바이트다. 앞의 등비수열 합 공식에 넣으면, $1/2^n$은 매우 작아서 무시할 수 있으므로 비트맵 전체 크기는 다음과 같다.

$$
2a\left(1-\frac{1}{2^n}\right) \approx 2a = 2 \cdot \frac{N}{8} = \frac{N}{4}
$$

여기에 원래 페이지마다 4바이트짜리 참조 카운트 배열이 따로 있었으므로 $4N$바이트를 더해야 해서, 합은 $17N/4$바이트다.

free list 버전은 페이지마다 20바이트짜리 `struct page`를 두므로 $20N$바이트다.

$$
20N : \frac{17N}{4} \approx 4.7 : 1
$$

free list 버전이 메모리를 약 4.7배 더 사용한다. RAM이 4GB라면 비트맵 버전은 약 4.25MB, free list 버전은 20MB를 사용한다. RAM 대비로는 $20 / 4096 \approx 0.5\%$로, 할당이 $O(N)$에서 $O(1)$이 된 것에 비하면 충분히 감수할 만한 비용이다.
