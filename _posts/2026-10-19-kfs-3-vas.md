이번 글에서는 페이지 크기 설계와, 커널 가상 주소 공간을 관리하는 방법을 정리한다.

## Page Size

유저 공간은 4KB 페이지를, 커널 공간은 4MB 페이지를 사용한다. 4MB 페이지에는 두 가지 큰 장점이 있다.

1. **TLB 효율**: TLB는 크게 페이지 크기와 상관없이 엔트리를 함께 쓰는 통합형과, 큰 페이지용 엔트리를 따로 두는 분리형이 있다. 통합형이라면 4KB 페이지로 1024개가 필요했던 엔트리가 하나로 줄어든다. 분리형이라면 큰 페이지를 쓰지 않는 한 큰 페이지 전용 엔트리는 전부 낭비된다.
2. **페이지 워크 단계 감소**: PAE를 켜지 않은 x86의 페이지 워크는 3단계로 이루어진다. PSE로 4MB 페이지를 쓰면 페이지 디렉터리 엔트리가 페이지 테이블 대신 4MB 페이지를 직접 가리키므로, 페이지 워크가 한 단계 줄어든다.

![4KB 페이지와 4MB 페이지의 페이지 워크 비교](/assets/img/kfs/kfs-page-walk.png)
_Page walk for a 4KB page and a 4MB page_

단점은 내부 단편화가 커진다는 것이다. 내부 단편화는 그 자체로 메모리 낭비이고, 페이지를 스왑 인할 때 필요 없는 데이터까지 함께 옮기게 만든다. 또 스왑 단위가 커지니 페이지 하나를 스왑 인하는 지연도 커진다.

하지만 커널에서는 이런 단점이 크게 줄어든다.

1. 내부 단편화는 쌓일수록 문제가 커진다. 유저 공간에 4MB 페이지를 쓰면 프로세스마다 단편화가 생기지만, 커널은 하나뿐이라 단편화가 프로세스 수만큼 쌓이지 않는다.
2. 커널 페이지는 스왑 아웃되지 않으므로 스왑 문제가 생기지 않는다.

결국 커널에서의 이러한 단편화는 낭비라기보다, 약간의 메모리를 써서 TLB 성능을 끌어올리는 선택에 가깝다.

대신 포기한 것도 있다. 4MB 페이지를 사용하면 패딩이 너무 커져서, 커널의 `.text`나 `.rodata` 같은 섹션에 읽기 전용 보호를 걸 수 없다.

## Kernel Virtual Address Space

커널 가상 주소 공간 관리 코드: [src/kernel/vmm.c](https://github.com/zerone015/kfs/blob/master/src/kernel/vmm.c)

커널 가상 주소 공간은 다음 두 구조체와 연결 리스트로 관리한다.

```c
#define K_VBLOCK_MAX        (K_VSPACE_SIZE / PAGE_LARGE_SIZE / 2)

struct k_vblock {
    uintptr_t base;
    size_t size;
    struct list_head list_head;
};

struct k_vblock_pool {
    struct k_vblock *objs[K_VBLOCK_MAX];
    int top;
};

static struct list_head free_list;              /* free kernel vblocks */
static struct k_vblock objs[K_VBLOCK_MAX];
static struct k_vblock_pool obj_pool;           /* free k_vblock objects */
```

`struct k_vblock`은 커널 가상 주소 공간의 연속된 빈 블록 하나를 나타낸다. `base`에 시작 주소, `size`에 크기가 들어가고, `list_head`는 연결 리스트에 쓰이는 임베드된 링크다. `free_list`는 이 구조체들을 잇는 연결 리스트로, 사용 가능한 커널 가상 블록들을 관리한다.

`objs`는 `struct k_vblock`의 배열이다. 배열 크기인 `K_VBLOCK_MAX`는 빈 블록이 동시에 존재할 수 있는 최대 개수다. 해제할 때 인접한 빈 블록끼리 병합하므로 빈 블록은 서로 붙어 있을 수 없고, 빈 블록과 사용 중인 블록이 번갈아 있을 때 개수가 가장 많아진다. 그래서 커널 가상 주소 공간의 4MB 블록 개수를 2로 나눈 것이다.
`free_list`가 빈 블록을 관리한다면, `obj_pool`은 그 블록을 나타낼 구조체 자체를 관리한다. 지금 어떤 블록도 나타내고 있지 않은 `struct k_vblock`을 담아 두는 free stack으로, 이게 없으면 새 빈 블록이 생길 때마다 `objs`에서 쓰이지 않는 구조체를 탐색해야 한다. 할당할 때는 `free_list`의 블록에서 요청 크기만큼 잘라 내고, 남는 부분이 없으면 그 구조체를 스택에 돌려놓는다. 해제할 때는 스택에서 구조체를 하나 꺼내 주소와 크기를 기록한 뒤 `free_list`에 추가한다.

`obj_pool`을 비트맵으로 만들지도 고민했다. 구조체 개수를 $N$이라 하면 비트맵은 $N/8$바이트를, 스택은 포인터 $N$개와 `top`을 합쳐 $4N + 4$바이트를 사용한다.

$$
4N + 4 : \frac{N}{8} \approx 32 : 1
$$

스택이 메모리를 약 32배 더 쓰지만, 스택은 $O(1)$로 꺼내고 넣을 수 있는 반면 비트맵은 빈 자리를 찾아야 해서 $O(N)$이다. 게다가 커널 가상 주소 공간이 1GB라 $N$이 128밖에 되지 않아서, 스택도 516바이트면 충분하다. 메모리 차이는 사실상 없는데 성능 차이는 크니 고민할 필요가 없었다.

### Initialization

초기화 코드: [src/kernel/vmm.c](https://github.com/zerone015/kfs/blob/master/src/kernel/vmm.c#L188)

```c
void vmm_init(void)
{
    vb_init();
    vb_pool_init();
}
```

`vb_init`은 페이지 디렉터리를 순회하며 비어 있는 영역을 찾아 `free_list`에 넣는다. 초기화 직후의 `free_list`에는 큰 빈 블록 하나만 들어 있는데, `pgmap`이 끝나는 지점부터 임시 매핑 영역 직전까지 이어지는 연속된 빈 공간이다.

![가상 주소 공간 초기화 직후의 커널 가상 주소 공간](/assets/img/kfs/kfs-vmm.png)
_Kernel virtual address space after virtual address space initialization_

`vb_pool_init`은 `objs`의 원소들을 `obj_pool`에 넣는다. 방금 `vb_init`에서 쓴 원소 하나만 빼고 전부 넣는다.

### Allocation

할당 코드: [src/kernel/vmm.c](https://github.com/zerone015/kfs/blob/master/src/kernel/vmm.c#L145)

할당은 `free_list`를 앞에서부터 탐색해서, 요청 크기를 담을 수 있는 첫 번째 블록을 사용하는 first-fit 방식이다. 블록이 요청보다 크면 분할하는데, 이때 항상 블록의 뒤쪽을 떼어 내서 할당한다. 그러면 남은 블록은 `base`를 그대로 두고 `size`만 줄이면 된다. 블록이 요청 크기와 딱 맞으면 블록을 `free_list`에서 빼고 구조체를 `obj_pool`에 돌려놓는다.

빈 블록을 고르는 방식에는 first-fit 외에도 best-fit과 worst-fit이 있다. first-fit은 가장 빠르지만 리스트 앞쪽에 작은 블록들이 몰리는 경향이 있다. best-fit은 요청 크기에 가장 가까운 블록을 고르기 때문에 쓰기 어려운 작은 조각이 많이 생기고, 리스트 전체를 탐색해야 해서 first-fit보다 느리다. worst-fit은 가장 큰 블록에서 잘라 남는 조각을 크게 남기려는 방식이지만, 역시 전체를 탐색해야 하고 큰 블록이 금방 쪼개져서 큰 요청을 처리하지 못하게 된다. 그중 가장 빠른 first-fit을 택했다.

할당할 때는 가상 주소 공간만 예약하고, 물리 페이지는 그 주소에 실제로 접근해 페이지 폴트가 났을 때 핸들러에서 할당한다. 당장 쓰지 않는 메모리에 물리 페이지를 낭비하지 않기 위해서다. 예를 들어 8MB를 할당해도 앞쪽 4MB에만 접근했다면, 물리 페이지는 그 4MB에만 할당된다.

예약 상태와 블록의 크기는 페이지 디렉터리 엔트리에 기록한다. x86의 페이지 디렉터리 엔트리와 페이지 테이블 엔트리에는 AVL로 표시된 비트들이 있는데, CPU가 사용하지 않아서 커널이 자유롭게 쓸 수 있다.

![4MB 페이지 디렉터리 엔트리와 페이지 디렉터리 엔트리의 비트 구성](/assets/img/kfs/kfs-pde.png)
_Page directory entry (source: OSDev Wiki)_

![페이지 테이블 엔트리의 비트 구성](/assets/img/kfs/kfs-pte.png)
_Page table entry (source: OSDev Wiki)_

AVL 중 9~11번 비트를 다음과 같이 사용한다.

```c
#define PG_RESERVED     0x800   /* lazy mapping / reserved entry */
#define PG_COW_RDWR     0x200   /* originally writable */
#define PG_COW_RDONLY   0x400   /* originally read-only */
#define PG_CONTIGUOUS   0x200   /* part of the same virtual block */
```

`PG_COW_RDWR`와 `PG_COW_RDONLY`는 COW에 쓰이는 비트로 유저 공간에서만 사용하고, `PG_CONTIGUOUS`는 커널 공간에서만 사용한다. 그래서 9번 비트를 둘이 함께 쓴다.

- **`PG_RESERVED`**: 지연 할당을 위한 비트. 할당된 블록의 엔트리에는 present 비트 없이 이 비트만 설정해 두고, 페이지 폴트 핸들러는 이 비트를 보고 물리 페이지를 할당해 매핑한다.
- **`PG_CONTIGUOUS`**: 할당된 블록의 크기를 알아내기 위한 비트. 블록의 마지막 엔트리를 제외한 모든 엔트리에 이 비트를 설정한다. 그래서 할당된 블록은 구조체로 따로 관리하지 않아도, 엔트리를 따라가다 이 비트가 없는 엔트리를 만나면 블록이 끝난다는 걸 알 수 있다.

### Free

해제 코드: [src/kernel/vmm.c](https://github.com/zerone015/kfs/blob/master/src/kernel/vmm.c#L137)

해제는 먼저 `PG_CONTIGUOUS`를 따라 페이지 디렉터리 엔트리를 순회하며 블록의 크기를 잰다. 이때 present 비트가 켜진 엔트리는 물리 페이지가 매핑되어 있다는 뜻이므로, 그 물리 페이지를 버디 할당자에 반납하고 해당 주소의 TLB 엔트리를 무효화한다.

그다음 `obj_pool`에서 구조체를 하나 꺼내 해제할 주소와 방금 잰 크기를 기록하고, `free_list`에 넣는다. `free_list`를 앞에서부터 탐색하다가 해제할 주소보다 큰 주소의 블록을 만나면 그 블록 앞에 넣는다. 그리고 앞뒤 블록과 주소가 이어져 있으면 병합하고, 병합으로 남는 구조체는 `obj_pool`에 돌려놓는다. 이렇게 넣기 때문에 `free_list`의 블록들은 항상 주소 순으로 정렬되어 있다.

## User Virtual Address Space

커널 공간은 연결 리스트로 관리하지만, 유저 공간은 다르게 관리한다. 유저 공간은 3GB이고 페이지 크기가 4KB라서 페이지가 약 78만 개나 된다. 블록이 최대 128개였던 커널 공간과는 비교가 안 될 만큼 많아서, 따로 측정해 보지 않아도 연결 리스트로는 무리라고 판단했고 red-black tree를 선택했다.

red-black tree를 쓰려면 무엇을 key로 할지 정해야 하는데, 후보는 `base`와 `size`다. `base`를 key로 하면 해제할 때 병합할 인접 블록을 찾는 트리가 되고, `size`를 key로 하면 할당 요청 크기에 맞는 블록을 찾는 트리가 된다. 할당과 해제 모두 $O(\log n)$을 유지하려면 두 트리를 모두 유지해야 한다.

red-black tree는 intrusive 자료구조로 구현했다. 링크가 데이터 안에 임베드되어 있어서, 같은 데이터를 여러 트리에 넣을 때도 데이터를 복제할 필요 없이 링크만 여러 개 두면 되므로 메모리를 아낄 수 있다. 삭제도 빠르다. 각 트리가 노드를 따로 복제해 갖고 있다면 트리마다 탐색해야 하지만, intrusive 구조에서는 한 번 찾은 데이터 안에 모든 트리의 링크가 들어 있어서 한 번의 탐색으로 모든 트리에서 제거할 수 있다. 연결 리스트도 같은 intrusive 구조로 구현했고, 이 코드들은 리눅스 커널의 구현을 가져와 내 커널에 맞게 이식했다.

![하나의 u_vblock이 두 red-black tree에 동시에 연결된 모습](/assets/img/kfs/kfs-intrusive-rbtree.png)
_Each u\_vblock is linked into both trees through its own embedded nodes_

```c
/* User allocatable virtual-address block */
struct u_vblock {
    struct rb_node by_base;
    struct rb_node by_size;
    uintptr_t base;
    size_t size;
};

/* User vblock red-black trees */
struct u_vblock_tree {
    struct rb_root by_base;
    struct rb_root by_size;
};

/* Mapped-region virtual-address block */
struct mapped_vblock {
    struct rb_node by_base;
    uintptr_t base;
    size_t size;
};

/* Mapped-region tree */
struct mapped_vblock_tree {
    struct rb_root by_base;
};
```

유저 공간은 커널 공간과 달리 할당된 블록도 관리한다. 유저 공간의 메모리는 익명 메모리와 파일 매핑 메모리로 나뉠 예정이었는데, 파일 매핑 메모리는 참조 관리나 변경 내용의 반영 같은 추가 처리가 필요하기 때문이다. `u_vblock`은 사용 가능한 블록이고, `mapped_vblock`은 할당된 블록이다. `u_vblock_tree`는 사용 가능한 블록의 두 트리를, `mapped_vblock_tree`는 할당된 블록의 트리를 담는다.

유저 공간은 부팅할 때 초기화되지 않는다. 메타데이터는 프로세스의 `task_struct`에 들어 있고, fork할 때 복제된다. 유저 공간의 할당과 해제는 원래 `mmap`과 `munmap`의 역할인데, 아직 구현하지 않았다. `execve`도 아직 없지만, 유저 공간 테스트를 위해 비슷한 역할을 하는 `exec_fn`이 있다. 이 구조가 실제로 쓰이는 곳은 fork와 exit, `exec_fn`을 다루는 글에서 설명한다.

### Cleanup

클린업 코드: [include/vmm.h](https://github.com/zerone015/kfs/blob/master/include/vmm.h#L165)

```c
static inline __attribute__((always_inline))
void user_vas_cleanup(struct u_vblock_tree *vblocks,
                      struct mapped_vblock_tree *mapped_vblocks,
                      int flags)
{
    vblocks_cleanup(vblocks);
    mapped_vblocks_cleanup(mapped_vblocks,
                           flags & CL_MAPPING_FREE,
                           flags & CL_TLB_INVL);
    pgdir_cleanup(flags & CL_RECYCLE);
}
```

`user_vas_cleanup`은 exit, `exec_fn`, fork의 롤백에서 사용하는 클린업 함수로, 다음 순서로 진행된다.

1. 사용 가능한 블록 트리를 순회하며, 구조체에 할당했던 힙 메모리를 해제한다.
2. 할당된 블록 트리를 순회하며 물리 페이지를 해제하거나 참조 카운트를 줄이고, TLB를 무효화한 뒤 구조체를 해제한다.
3. 페이지 디렉터리의 유저 영역을 순회하며 페이지 테이블을 해제한다. 페이지 디렉터리를 재사용할 때는 엔트리를 0으로 초기화하고 TLB도 무효화한다.

대부분은 공통된 작업이지만, 일부는 진입 경로마다 다르다.

- 2번의 물리 페이지 해제는 fork의 롤백에서는 필요 없다. 롤백은 자식이 물리 페이지를 공유하기 전에 일어나기 때문이다.
- TLB 무효화는 exit에서는 필요 없다. 이 프로세스는 다시 스케줄되지 않기 때문이다.
- 3번에서 엔트리를 0으로 초기화하는 건 페이지 디렉터리를 다시 쓰는 `exec_fn`에서만 필요하다. exit에서는 페이지 디렉터리 자체를 버리기 때문에 필요 없다.

이 차이를 하나의 함수로 처리하기 위해 플래그를 사용한다.

- **`CL_MAPPING_FREE`**: 할당된 블록의 물리 페이지를 해제할지
- **`CL_TLB_INVL`**: 할당된 블록을 해제하면서 TLB도 무효화할지
- **`CL_RECYCLE`**: 페이지 디렉터리를 재사용할 수 있도록 엔트리를 초기화할지

플래그는 항상 컴파일 타임 상수로 넘기기 때문에, 함수가 인라인되면 컴파일러가 쓰이지 않는 분기를 제거할 수 있다. 그래서 인라인을 보장하도록 `__attribute__((always_inline))`을 붙였다.
